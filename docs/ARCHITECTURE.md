## Бэкенд: модульный монолит

`backend/internal/` разделён на платформу и доменные модули.

- `platform/` — инфраструктура без бизнес-логики: `config` (строгая загрузка env), `logger`
  (slog JSON с атрибутами из контекста), `db` (пул pgx, транзакции с областью RLS), `cache`
  (Valkey), `httpx` (RFC 9457, middleware, Idempotency-Key), `health`, `metrics`
  (Prometheus), `telemetry` (OpenTelemetry), `migrate` (goose + River), `apperr` (доменные ошибки
  со стабильными кодами), `testpg` (Postgres в testcontainers для интеграционных тестов).
  Платформенные пакеты фазы 2: `authz` (принципал и проверка ролей), `tenancy` (вуз запроса),
  `secrets` (ключи HKDF из мастер-секрета, AES-GCM), `ratelimit` (GCRA на Valkey), `jobs`
  (постановка задач River в транзакции), `pagination` (курсоры), `validate` (проверка полей).
- Доменные модули устроены одинаково: пакет `internal/<module>` содержит `Service` (бизнес-правила
  и проверки прав) и `Handler` (операции своего тега OpenAPI), доступ к своим таблицам — через
  sqlc-пакет `internal/<module>/<module>db`, фоновые задачи — River-воркеры модуля.
  Реализованы: `system`, `tenant` (определение вуза по адресу, настройки), `auth` (пароли, коды,
  SSO, сессии, CSRF, отзыв), `directory` (вход через Active Directory / LDAP: настройки вуза и
  проверки), `user` (участник, профиль, онбординг, каталог участников), `org`
  (факультеты, кафедры, группы), `files` (S3, ClamAV, аватары), `team` (доска «Ищу в команду»),
  `imports` (CSV/XLSX), `audit`, `mail` (письма на трёх языках через очередь), `ai` (шлюз
  языковых моделей и диалоги), `knowledge` (база знаний вуза с векторным поиском), `project`
  (проекты, команды, права доступа), `incubator` (14 шагов, история, комментарии, присутствие,
  AI-ментор, материалы), `evaluation` (AI-оценка по рубрике, корректировки экспертов, PDF-отчёт).
  Далее: `showcase`, `competition`, `mentorship`, `analytics`, `certificate`,
  `notification`, `telegram`, `webhooks`.
- `app/` собирает модули: `api.go` — роутер и композиция хендлеров, `worker.go` — регистрация
  воркеров и очередей (`default`, `mail`). `seed/` — демо-данные и тестовые фикстуры.

Модули общаются через интерфейсы сервисов и доменные события, а не через чужие таблицы.

### Жизненный цикл запроса

1. `RequestID` (X-Request-ID, в логах), `ClientIP` (последняя запись X-Forwarded-For, только от
   доверенного прокси — одного хопа Nginx), `Recoverer` (panic → 500 problem), OpenTelemetry-спан
   с именем маршрута, метрика длительности по шаблону маршрута (метод — из фиксированного набора),
   access-лог без query-строки, security-заголовки.
2. Для `/api/v1`: таймаут контекста (кроме SSE-маршрутов), лимит тела (больше для маршрутов
   загрузки); оба набора маршрутов читаются из `openapi.yaml`, а не из заголовков запроса,
   определение вуза по `Host` (точный домен → `<slug>.<base>` → вуз по умолчанию только для базового
   домена, хоста `PUBLIC_URL` и localhost; прочие хосты — `tenant.not_found`; область RLS
   ставится в контекст), CSRF (`Sec-Fetch-Site`, `Origin`, double submit), аутентификация по
   cookie `qadam_at` (JWT + проверка отзыва и версии ролей в Valkey), Idempotency-Key для POST
   (ключи привязаны к участнику или IP).
3. Сгенерированный роутер разбирает параметры, strict-хендлер декодирует тело в типы из спеки.
4. Хендлер вызывает сервис; сервис открывает `db.Tx` с областью тенанта; ошибки — `*apperr.Error`.
5. Ответ — типизированная структура из спеки или problem+json с локализуемым `code`.

### Аутентификация и сессии

- Вход: пароль (argon2id), код из письма (6 цифр, 10 минут, 5 попыток на код и не больше 10 в
  сутки на аккаунт), SSO вуза по OIDC (Authorization Code + PKCE, nonce, состояние в зашифрованной
  cookie; привязка к существующему аккаунту — только к участнику этого вуза или адресу на его домене).
  Регистрация — с согласием на обработку данных конкретным вузом; сессия начинается только после
  перехода по ссылке из письма, вход паролем до подтверждения почты — `auth.email_unverified`.
- Смена и сброс пароля, «выйти везде» отзывают сессии аккаунта во всех вузах (узкий системный запрос
  по `user_id`).
- Сессия — строка `sessions`; access-токен (JWT, 15 мин) и ротируемый refresh-токен (30 дней) —
  в httpOnly cookie. Повторное предъявление старого refresh-токена отзывает сессию. Отзыв и смена
  ролей действуют немедленно (deny-list и версия ролей в Valkey). Подробно — D-022.
- Письма (подтверждение почты, коды, сброс пароля, приглашения, отклики) ставятся задачей River в
  транзакции бизнес-изменения; адрес и данные письма в таблице задач зашифрованы.

### Вход через каталог вуза (Active Directory / LDAP)

```
 браузер ── POST /auth/directory/login {username, password}
   │
 auth.Service.DirectoryLogin ──► directory.Service.Authenticate (auth.DirectoryAuthenticator)
   │                               │ включён ли каталог вуза; пустой пароль → 422 без запроса к серверу;
   │                               │ лимиты (адрес — общий с паролем, логин — 5 за 15 мин)
   │                               ▼
   │                             LDAP: ldaps:// или StartTLS (CA вуза) → bind сервисной записи →
   │                             поиск по фильтру с экранированным логином (не больше 2 записей) →
   │                             bind пользователя его паролем → группы (memberOf, вложенные) →
   │                             обязательная группа, почта, роли по сопоставлениям
   │                               │ отказ: единый ответ, не раньше 0,8 с, auth.login_failed в аудит
   ▼                               ▼
 auth.SignInExternal (общий с SSO): идентичность ldap:<вуз> → привязка по почте по D-067 →
 создание аккаунта и членства / синхронизация управляемых ролей → admit → auth.login → сессия
```

- Модуль `directory` владеет таблицей `tenant_directory_settings` (RLS) и разговором с каталогом
  (`go-ldap`); аккаунты, сессии и правила привязки — у `auth`. `GET /tenant` сообщает странице входа,
  включён ли каталог (`directory_login`, через интерфейс `tenant.LoginOptions`).
- Администратор вуза настраивает всё на `/app/admin/directory`: пресеты (AD, OpenLDAP, FreeIPA),
  проверка подключения по шагам и проверка пользователя без пароля работают с несохранёнными
  настройками; включить вход можно только с доказательством успешной проверки того же соединения.
  Пароль сервисной учётной записи хранится зашифрованным и не возвращается. Подробно — D-NEW,
  инструкция для вуза — `docs/guides/active-directory.md`.
- Разработка: `docker-compose.dev.yml` поднимает OpenLDAP с демо-каталогом КазУТБ (`deploy/ldap`),
  интеграционные тесты — тот же образ через testcontainers (`internal/directory/ldaptest`).

### Данные и изоляция тенантов

- PostgreSQL 17: UUIDv7, `citext`, `pg_trgm`, `pgvector`.
- Каждая таблица с `tenant_id` — под RLS. `db.Tx` выставляет `app.tenant_id`/`app.system`
  транзакционно-локально; приложение подключается ролью `qadam_app`, на которую RLS действует
  всегда. API, worker и seed при старте отказываются работать под суперпользователем, ролью с
  BYPASSRLS или владельцем таблиц. Подробности — `docs/DECISIONS.md` (D-006).
- Миграции — goose (SQL, встроены в бинарник); очередь River хранит задачи в той же БД, поэтому
  задача ставится в одной транзакции с бизнес-изменением.

### AI-слой

```
 модуль (ментор, оценка, генерация)
   │  ai.Call{feature, prompt@version, schema?}
   ▼
 ai.Gateway ── лимиты (ai_usage за сутки) ── маршрут вуза → QADAM_AI_ROUTES → QADAM_AI_DEFAULT
   │              │
   │              └─ «только локальные» — внешние провайдеры исключаются
   ▼
 для внешнего провайдера: маскирование ИИН/телефонов/почты ──► llm.Provider ──► восстановление меток
   │                                                       anthropic │ openai-совместимый │ mock
   ▼
 проверка JSON Schema (одна попытка исправления) → запись в ai_usage → ответ / поток SSE
   └─ ошибка или отказ → следующий провайдер цепочки
```

- `ai/llm` — интерфейс провайдера и общие типы; `ai/anthropic` (официальный Go SDK, Messages
  API: `output_config.effort/format`, кеширование системного промпта, серверные резервные модели
  для Opus), `ai/openai` (chat/completions и embeddings, потоки SSE, `response_format` со схемой),
  `ai/mock` (детерминированные ответы на трёх языках, значения по JSON Schema, эмбеддинги
  hashing trick) — D-031.
- `ai/schema` — проверка ответа по JSON Schema 2020-12 и упрощение схемы для constrained decoding;
  `ai/redact` — маскирование персональных данных с обратной заменой, в том числе в потоке (D-032);
  `ai/prompts` — версионируемые шаблоны промптов, данные пользователя только внутри тегов (D-033).
- Учёт: каждая попытка — строка `ai_usage` (вуз, пользователь, функция, провайдер, модель, версия
  промпта, токены, кеш, стоимость, задержка, статус). Лимиты на пользователя и вуз — D-034: идущий
  вызов держит резерв токенов в `ai_reservations`, эмбеддинги учитываются, но в лимит не входят.
- Потоки: `httpx.SSE` (события `delta`, `done`, `error`, комментарий-heartbeat каждые 15 с тишины),
  отмена — закрытие соединения клиентом отменяет контекст запроса и вызов модели; Nginx не
  буферизует `text/event-stream`. Сбой провайдера до первых слов — переход к следующему в цепочке.
- OpenAI-совместимый адаптер: таймаут — на ожидание начала ответа и паузы потока, а не на весь
  ответ; 429, 5xx и сбои сети до ответа повторяются с растущей паузой.
- База знаний: документ (PDF, DOCX, TXT, Markdown или текст) → проверка антивирусом → извлечение
  текста (не больше 4 МБ) → задача `knowledge.index` (фрагменты по ~900 символов с заголовком
  раздела → эмбеддинги одной модели → pgvector). Поиск — косинусная близость среди фрагментов той
  же модели с порогом релевантности, иначе полнотекстовый (D-030). Задача `knowledge.reindex` раз в
  час ставит на индексацию документы без фрагментов текущей модели (смена модели, сбои), но не
  больше трёх неудачных раз подряд.
- Фоновые задачи AI (оценка, материалы, индексация) записывают провал на отдельном контексте; задача
  `platform.fail_stale` раз в 10 минут переводит в `failed` записи, чья задача пропала (падение или
  выкладка worker), — после худшего времени всех попыток.
- Настройка провайдеров — переменные `QADAM_AI_*` (README, `.env.example`) и экран администратора
  вуза «AI» (маршруты по функциям, режим только локальных моделей, лимиты, режим ментора,
  проверка подключения, отчёт о расходах).

### Инкубатор

- `project` хранит проекты и команды и решает, кто что может (D-040); прогресс считает
  `incubator` и сообщает обратно через интерфейс `project.ProgressSource` (без циклических
  зависимостей модулей).
- Шаги описаны данными (`incubator/template.yaml`, D-035). Ответы шага — JSONB с версией;
  сохранение требует `If-Match`, изменения полей пишутся ревизиями с автором и источником
  (`edit` / `mentor` / `restore`), откат — новой ревизией (D-036). Завершение шага проверяет
  минимумы шаблона; руководитель может одобрить шаг принудительно.
- AI-проверка шага (`step_check@1`) возвращает чек-лист по критериям в структурированном виде;
  AI-ментор (`mentor@2`) стримит ответ по SSE и опирается на ответы проекта и базу знаний (D-038).
- Комментарии к шагу или полю с ветками и @упоминаниями; присутствие и версии шагов — опросом
  через Valkey (D-037); лента активности собирается из ревизий, комментариев, завершений и
  вступлений в команду.
- Материалы (one-pager, питч-дек PDF/PPTX, паспорт с QR) — задача River `incubator.material`:
  тексты модели → HTML-шаблоны → Gotenberg → файл в S3 (D-039).

### AI-оценка

- Запрос оценки сохраняет снимок рубрики вуза и ставит задачу River `evaluation.run`; воркер
  собирает данные проекта (`incubator.ProjectContext`) и записывает версии шагов, которые прочитал,
  вызывает модель с промптом `evaluation@2` и схемой ответа (не дольше 9 из 10 минут задачи),
  проверяет покрытие рубрики, считает итог и уровень (D-041). Карточки проектов показывают последнюю оценку (`project.EvaluationSource`).
- Отчёт сравнивает оценку с предыдущей (итог и баллы критериев), показывает корректировки
  экспертов; PDF рендерится через Gotenberg по запросу.
- `make ai-eval` проверяет промпт и модель на золотых проектах через AI-шлюз тем же кодом, что и
  worker (`evaluation.Evaluate`), — D-042 и решение о харнессе в конце `DECISIONS.md`.

### Брендинг вуза

- `tenants.logo_file_id` (печать) и `tenants.cover_file_id` (фото кампуса) — публичные файлы вуза
  (`tenant_logo`, `tenant_cover`), отдаются в `GET /tenant` как `logo_url` и `cover_url` и в
  `tenant.University.CoverURL` для страниц, которые рисует сервер. Без них интерфейс показывает знак
  Qadam и заливку (D-051).

### Витрина

- `showcase` хранит страницы проектов (`showcase_entries`) и запросы на контакт
  (`contact_requests`). Страница предзаполняется из ответов инкубатора
  (`incubator.DraftShowcase`), команда и балл последней оценки берутся из модулей `project` и
  `evaluation` при каждом сохранении. Статусы и видимость — D-043; видимость проекта
  синхронизируется через `project.SetVisibility`.
- Публичные операции (`GET /showcase`, `/showcase/facets`, `/showcase/highlights`,
  `/showcase/entries/{slug}`, форма контакта, `og.png`) работают без входа: область каталога —
  публичные страницы вуза адреса, его же страницы для вошедших участников или публичные страницы
  всех вузов (`scope=national`, через RLS-политику, D-044). Поиск — `tsvector` + префиксные термы
  (D-048).
- Поисковым системам и превью ссылок: Nginx → API → оболочка `index.html` с подставленными
  метаданными, JSON-LD и `<noscript>`-текстом; `sitemap.xml`, `robots.txt` (D-045). Для главной,
  каталога и страницы проекта API рисует и первый экран (`#boot`, шаблон `boot.html` с классами
  клиента) на языке, который выберет клиент (cookie `qadam_locale` → `Accept-Language` → kk);
  клиент рисует ту же страницу под ним и убирает его, когда страница готова (`src/app/boot.ts`,
  D-050).
  OG-картинки — скриншот HTML через Gotenberg, кэш по хэшу показанных данных (D-046).
- Запросы на контакт: ловушка для ботов и лимиты, модерация по настройке вуза, письмо команде
  через `mail.Mailer` в той же транзакции (D-047). Паспорт стартапа ведёт QR-кодом на публичную
  страницу (`incubator.PageSource`).

## Фронтенд

- `src/app` — роутер (file-based маршруты в `src/app/routes`), провайдеры, layout-ы.
- `src/design-system` — дизайн-система (витрина: `/design`):
  - `tokens.css` — шкалы цветов в OKLCH (`@theme static`), семантические токены светлой и тёмной
    темы (`@theme inline` → `--qd-*`), радиусы, три уровня теней, движение; `base.css` — базовые
    стили, фокус, reduced motion, утилиты `font-display`, `surface-glass`, `ornament`, `shimmer`;
  - `components/` — около 40 компонентов на Radix (кнопки, поля с `Field`, выбор, оверлеи, тосты,
    навигация, `Stepper`, KPI, `ScoreGauge`, командная палитра ⌘K, переключатели темы и языка);
  - `illustrations/` — 10 иллюстраций пустых состояний в едином стиле; `color.ts` — генерация
    шкал и контраст WCAG (для палитр тенантов); `theme.ts` — тема (light/dark/system).
- `src/app/layouts` — `PublicLayout`, `AuthLayout`, `AppShell` (сайдбар, ⌘K), `WorkspaceLayout`
  (три колонки инкубатора).
- `src/features/<feature>` — экраны и хуки фич (`api.ts` с queryOptions).
- `src/shared` — API-клиент (`schema.gen.ts` из `openapi.yaml`, `unwrap`, `ApiError`), i18n, утилиты.
- `src/locales/{kk,ru,en}` — переводы по пространствам имён; язык грузится лениво.

## Развёртывание

Docker Compose поднимает весь стек одной командой (`make dev`): postgres, valkey, minio,
одноразовые `minio-init` и `migrate`, gotenberg, clamav, api, worker, web, а в разработке ещё
mailpit. Один образ бэкенда содержит все бинарники (`/app/api`, `/app/worker`, `/app/migrate`).

- `deploy/docker-compose.yml` — базовый файл: наружу опубликован только web (Nginx, `WEB_PORT`),
  API и служебные сервисы доступны только во внутренней сети compose. Valkey — с паролем
  (`VALKEY_PASSWORD`). Корневые ключи MinIO видят только `minio` и `minio-init`; последний при
  каждом старте создаёт бакет и пользователя приложения (`S3_ACCESS_KEY`) с правом читать и
  писать только объекты этого бакета (`deploy/minio/init.sh`).
- `deploy/docker-compose.dev.yml` — только для машины разработчика: порты API, PostgreSQL,
  Valkey, MinIO, Gotenberg и ClamAV на `127.0.0.1` (`DEV_BIND`), Mailpit, куда уходят все письма,
  и OpenLDAP с демо-каталогом КазУТБ для входа через каталог (`LDAP_PORT`).
  В продакшне конфигурация отказывается стартовать с `QADAM_SMTP_HOST=mailpit`, без
  `QADAM_SMTP_FROM`, без пароля Valkey и с паролями из `.env.example`.
- IP клиента. Nginx записывает в `X-Forwarded-For` адрес, который видит сам (`$remote_addr`), а не
  дописывает присланный клиентом; API доверяет одному хопу и берёт последнюю запись заголовка.
  Если перед контейнером web стоит TLS-прокси (фаза 12), Nginx должен сначала восстановить адрес
  клиента модулем realip: `set_real_ip_from <адрес прокси>;` и `real_ip_header X-Forwarded-For;`
  в блоке `server` — иначе все клиенты будут выглядеть одним адресом прокси и делить лимиты.
- Журнал доступа Nginx пишет путь без query-строки и без `Referer`: в ссылках из писем — одноразовые
  токены, в ответе SSO — коды. В журнал ошибок Nginx при недоступном API строка запроса попадает
  целиком; это касается только кода SSO, одноразового и короткоживущего.

Prod-конфигурация, TLS (Caddy), бэкапы и мониторинг — фаза 12 (`docs/OPERATIONS.md`).
