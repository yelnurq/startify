# Архитектурные решения

Формат: контекст → решение → последствия. Новые решения добавляются в конец.

## D-001. Ветка разработки
**Контекст.** Репозиторий пустой, работа идёт фазами с коммитом после каждой.
**Решение.** Вся работа ведётся в ветке `feat/qadam-platform`; в `main` изменения попадают слиянием (fast-forward).
**Последствия.** `main` остаётся чистым до приёмки; слияние — `git checkout main && git merge --ff-only feat/qadam-platform`.

## D-002. OpenAPI 3.1 и strict server oapi-codegen
**Контекст.** ТЗ требует OpenAPI-first и OpenAPI 3.1. oapi-codegen поддерживает 3.1 с версии 2.8.0 (июль 2026).
**Решение.** Единственный источник правды — `backend/api/openapi.yaml` (3.1). Go-код генерирует oapi-codegen 2.8 (`chi-server` + `strict-server`), TS-типы — openapi-typescript. Ответы, которым нужен прямой доступ к `http.ResponseWriter` (SSE-стримы, cookie, файлы), реализуются собственными типами, удовлетворяющими интерфейсу `…ResponseObject` strict-сервера.
**Последствия.** Хендлеры возвращают типизированные ответы или ошибку; ошибки централизованно превращаются в RFC 9457.

## D-003. TypeScript 5.9 вместо 7.0
**Контекст.** Актуальный TypeScript — 7.0 (нативный компилятор), но typescript-eslint поддерживает `<6.1`, а openapi-typescript — `^5`.
**Решение.** `typescript ~5.9.3`.
**Последствия.** Переход на 7.x — когда экосистема линтеров и генераторов его поддержит (`docs/BACKLOG.md`).

## D-004. sqlc: пакет на модуль, генерация в Docker
**Контекст.** Модули не должны трогать чужие таблицы. sqlc использует cgo-парсер PostgreSQL и не собирается на Windows без C-компилятора.
**Решение.** В `sqlc.yaml` отдельный блок на модуль (`db/queries/<module>` → `internal/<module>/<module>db`), `omit_unused_structs: true`. sqlc запускается из образа `sqlc/sqlc:1.31.1` (`make gen-sql`).
**Последствия.** Одинаковая версия генератора у всех разработчиков и в CI; CI проверяет, что сгенерированный код актуален.

## D-005. Инструменты разработки через `go tool`
**Решение.** oapi-codegen и golangci-lint закреплены в `backend/tools.mod` и вызываются `go tool -modfile=tools.mod …`.
**Последствия.** Нет глобальных установок; зависимости инструментов не попадают в `go.mod` приложения.

## D-006. Изоляция тенантов: сервисный слой + RLS
**Контекст.** ТЗ требует проверку в сервисном слое и Postgres RLS «вторым рубежом».
**Решение.** Каждая таблица с `tenant_id` защищена политикой `tenant_id = app_current_tenant() OR app_is_system()`. Область задаётся транзакционно-локальными настройками `app.tenant_id` / `app.system`, которые `db.Tx` берёт из контекста. API и worker работают от роли `qadam_app` (не владелец, без BYPASSRLS), миграции — от владельца схемы. Вне транзакции область не задана и RLS скрывает все строки тенантов (fail closed). Вложенные `Tx` — savepoint'ы; смена области во вложенном блоке откатывается после него.
**Последствия.** Забытый фильтр по тенанту даёт пустой результат, а не утечку; интеграционные тесты доказывают изоляцию на реальном Postgres.

## D-007. Пользователи глобальные, роли — в контексте тенанта
**Решение.** `users` и `user_identities` — общие для платформы (один человек может состоять в нескольких вузах); `memberships` (пользователь × тенант × роли) защищены RLS. Доступ администратора вуза к пользователям — только через членство в его тенанте.

## D-008. S3: MinIO из сборки Chainguard
**Контекст.** С конца 2025 года MinIO не публикует Docker-образы (`minio/minio` на Docker Hub недоступен), распространяется исходниками.
**Решение.** В compose используется `cgr.dev/chainguard/minio` — MinIO, собранный Chainguard из исходников upstream, закреплённый по digest (переопределяется `MINIO_IMAGE`). Приложение работает через S3 API (minio-go), поэтому хранилище заменяемо (RustFS, SeaweedFS, Ceph RGW, облачный S3 в РК).
**Последствия.** В образе нет curl, healthcheck хранилища выполняет само приложение (readiness).

## D-009. Idempotency-Key хранится в Postgres
**Решение.** Таблица `idempotency_keys` (scope = тенант + пользователь или IP для анонимных запросов, TTL 24 ч, очистка периодической задачей River). Повтор с тем же телом воспроизводит ответ (`Idempotent-Replayed: true`), с другим телом — 422 `idempotency.key_reused`, параллельный — 409 `idempotency.in_progress`, после 5xx ключ освобождается.
**Последствия.** Нет зависимости от доступности Valkey для корректности создающих запросов.

## D-010. Content Security Policy
**Решение.** `script-src 'self'` без inline-скриптов (тема применяется до отрисовки внешним `/theme-init.js`); `style-src 'self' 'unsafe-inline'` — inline-стили нужны библиотекам позиционирования (toasts, popovers). Встраивание видео — только YouTube (nocookie) и Vimeo.

## D-011. Язык по умолчанию и отсутствие fallback
**Решение.** Порядок выбора языка: сохранённый выбор → язык браузера → `kk` (настраивается `DEFAULT_LOCALE`, позже — тенантом). Runtime-fallback на другой язык отключён: в казахском интерфейсе не может появиться русская или английская строка. Полноту ключей гарантирует `npm run i18n:check` в CI, корректность ключей в коде — типы i18next.

## D-012. Конфигурация
**Решение.** Только переменные окружения `QADAM_*` (koanf + mapstructure). Неизвестная переменная `QADAM_*` — ошибка старта (защита от опечаток); все ошибки валидации выводятся разом. Переменные, нужные только Docker Compose, не имеют префикса `QADAM_`.

## D-013. Порты по умолчанию
**Контекст.** На машинах разработчиков часто уже запущены PostgreSQL, Redis, MinIO.
**Решение.** Наружу пробрасываются нестандартные порты (Postgres 54329, Valkey 63799, MinIO 9900/9901, Gotenberg 3300), все настраиваются в `.env`.

## D-014. Служебные эндпоинты
**Решение.** `/healthz`, `/readyz`, `/metrics` обслуживаются на порту API, но не проксируются Nginx наружу. Distroless-образы не содержат curl, поэтому healthcheck контейнеров — подкоманда бинарника (`/app/api healthcheck`).

## D-015. Race detector только в CI
**Контекст.** `go test -race` требует cgo; на Windows-машинах разработчиков C-компилятора обычно нет.
**Решение.** CI (Linux) всегда гоняет тесты с `-race`; локально — `GO_TEST_FLAGS=` при необходимости.

## D-016. Шрифт заголовков — Geologica (а не Unbounded или Manrope)
**Контекст.** ТЗ предлагает Unbounded или Manrope для заголовков и требует проверить казахские буквы.
Скрипт `npm run fonts:check` (fontkit, по правилам выбора `@font-face` из CSS Fonts 4) показал:
Unbounded не содержит Ә Ғ Қ Ң Ө Ұ Ү Һ, Manrope — Ә Ғ Қ Ң Ұ. Inter проходит полностью.
**Решение.** Интерфейс — Inter Variable, заголовки и крупные числа — Geologica Variable
(полный казахский алфавит; среди кандидатов Geologica/Onest/Montserrat/Golos/Inter Tight выбран
по визуальному сравнению). Оба шрифта self-hosted через `@fontsource-variable`, `font-display: swap`.
**Последствия.** Проверка глифов входит в CI и `make lint`; любой новый шрифт обязан её пройти.
**Обновлено.** Шрифты заменены решением D-049 (Google Sans и Literata); проверка глифов сохранена.

## D-017. Третичный текст — #667085, а не #8A94A6
**Контекст.** Цвет третичного текста из ТЗ (#8A94A6) даёт 2,95 : 1 на фоне #FAFBFC — ниже WCAG AA 4,5 : 1.
**Решение.** `fg-subtle` = #667085 (4,8 : 1) для подписей и плейсхолдеров; #8A94A6 сохранён как
`fg-faint` только для иконок, разделителей и декора. Аналогично текст и кнопки primary используют
ступень 700 (#007591, 5,3 : 1), а бренд-голубой #00A3C4 (≈ 500) — для декоративных элементов.
В тёмной теме кнопки primary — светлая заливка primary-400 с тёмным текстом (9,1 : 1).

## D-018. Палитра — `@theme static`, семантика — `@theme inline`
**Решение.** Шкалы (primary, gold, success, warning, danger, info, neutral) объявлены `@theme static`:
все CSS-переменные попадают в сборку, поэтому брендинг тенанта может переопределить
`--color-primary-*` во время выполнения. Семантические токены (`bg-surface`, `text-fg-muted`,
`bg-primary`…) — `@theme inline` поверх переменных `--qd-*`, которые переключает тема.
Собственный CSS ссылается только на `--qd-*` и шкалы, не на inline-токены.

## D-019. Контроль строк интерфейса линтером
**Решение.** `i18next/no-literal-string` в режиме `jsx-text-only` (текст между тегами) плюс
`no-restricted-syntax` для видимых атрибутов (`aria-label`, `placeholder`, `title`, `alt`, `label`)
и строковых литералов-детей `{'…'}`. Строки-ключи, классы и значения внутри JSX разрешены.
**Последствия.** Нельзя случайно оставить русскую строку в казахском интерфейсе, при этом код не
обрастает исключениями.

## D-020. Орнамент «қошқар мүйіз»
**Решение.** Собственный SVG-мотив (закрученные рога над ромбом, прямой и перевёрнутый в ромбической
решётке) как `mask-image` с цветом бренда: 5–7 % непрозрачности в hero с затуханием
(`ornament-fade`), 10–15 % белым на цветных обложках. Ни в интерфейсных элементах, ни в тексте
орнамент не используется.

## D-021. Файлы отдаются через API, а не по presigned URL
**Контекст.** Аватары, логотипы, вложения проектов хранятся в S3 (MinIO). Presigned URL обходят проверку прав и живут независимо от сессии.
**Решение.** Содержимое файла отдаёт `GET /api/v1/files/{id}/content`: метаданные читаются под RLS, права проверяются по видимости (`public` — всем, `tenant` — членам вуза, `private` — владельцу и администратору вуза), ответ стримится из S3. ETag = SHA-256, публичные файлы кешируются навсегда (`immutable`: содержимое по id не меняется). Небезопасные типы отдаются как `attachment` с `Content-Security-Policy: sandbox`. Аватары перекодируются в JPEG 512×512 (центр, EXIF-ориентация, без метаданных) и публичны — их id (UUIDv7, 74 случайных бита) не угадывается. Каждая загрузка проверяется ClamAV (`QADAM_FILES_SCAN`: `required` в продакшене — без антивируса загрузки отклоняются 503; `optional` в разработке). Удаление — мягкое; объекты удаляются задачей `files.purge` через сутки.
**Последствия.** Нагрузка трафика ложится на API (приемлемо для масштаба вуза; CDN можно поставить перед `/api/v1/files` для публичных файлов).

## D-022. Сессии: короткий access-токен + ротируемый refresh-токен в httpOnly cookie
**Решение.** Access — JWT HS256 на 15 минут (ключ выводится HKDF из `QADAM_AUTH_SECRET_KEY`), cookie `qadam_at` (`Path=/api`, `SameSite=Lax`, `HttpOnly`). Refresh — случайные 32 байта, в БД хранится SHA-256, cookie `qadam_rt` (`Path=/api/v1/auth`, `SameSite=Strict`), ротируется при каждом обновлении. Повтор старого refresh-токена в течение 30 с (параллельные вкладки) — 204 без новых cookie; позже — признак кражи: сессия отзывается целиком. Отзыв действует сразу: id сессии кладётся в deny-list Valkey на время жизни access-токена; смена ролей увеличивает «версию ролей» участника, и токены со старой версией отвергаются (клиент обновляет сессию и получает новые роли). При недоступности Valkey проверка закрывается (503), а не пропускает. CSRF: `Sec-Fetch-Site`/`Origin` отсекают межсайтовые запросы, при наличии сессионных cookie требуется заголовок `X-CSRF-Token`, равный cookie `qadam_csrf` (double submit); эндпоинты входа освобождены от double submit, чтобы устаревшая cookie не мешала войти снова.
**Последствия.** Токены недоступны JavaScript; украденный refresh-токен работает максимум до следующего обновления законным владельцем.

## D-023. Правовое основание обработки персональных данных
**Решение.** При самостоятельной регистрации пользователь даёт согласие на обработку данных конкретным вузом (текст и версия — в `tenant_settings`, версия и время согласия — в `memberships`; устаревшая версия отклоняется `auth.consent_required`). Студенты, загруженные импортом или созданные при входе через SSO вуза, обрабатываются на основании договора вуза со студентом (вуз — оператор данных по Закону РК «О персональных данных и их защите»), поэтому отдельного согласия у них не запрашивается.

## D-024. Связывание аккаунтов
**Решение.** Аккаунт (почта) глобален (D-007). Регистрация в другом вузе с той же почтой и верным паролем — это вступление существующего аккаунта в вуз; с неверным паролем — 409 `auth.email_taken`. Вход через SSO связывает существующий аккаунт с почтой только если провайдер подтверждает адрес (`email_verified: true`); иначе любой, кто управляет учётками IdP, мог бы захватить аккаунт. Вход по коду и переход по ссылке из письма подтверждают почту.

## D-025. Определение вуза по адресу
**Решение.** Порядок: точное совпадение домена (`tenant_domains`, например `innovation.kazutb.kz`) → поддомен базового домена (`kazutb.qadam.kz`, в разработке `kazutb.localhost`) → вуз по умолчанию (`QADAM_TENANT_DEFAULT`, для установки одного вуза). Ссылки в письмах ведут на адрес, с которого пришёл пользователь, только если адрес принадлежит вузу; для прочих хостов (подделанный `Host`) — на `QADAM_APP_PUBLIC_URL`, что исключает отравление ссылок сброса пароля. Найденные вузы кешируются на минуту, ненайденные — на 5 секунд. Приостановленный вуз (`status = suspended`) не обслуживается.

## D-026. Импорт студентов и структуры
**Решение.** Загрузка (CSV в UTF-8 или Windows-1251 с разделителем `;`/`,`/табуляцией, либо XLSX) сначала валидируется построчно в предпросмотр, изменения применяются отдельной командой с повторной валидацией. Неизвестные столбцы — ошибка (лучше отказать, чем молча потерять данные); заголовки принимаются на русском и казахском. Административные роли (`tenant_admin`, `leadership`) импортом не назначаются, роли существующих участников импорт не меняет. Названия факультетов и кафедр при обновлении сливаются по языкам. Новым участникам отправляется приглашение (ссылка на установку пароля, 7 дней).

## D-027. Пароли
**Решение.** argon2id с параметрами OWASP (19 МиБ, 2 прохода, 1 поток), не более `max(2, NumCPU)` вычислений одновременно (ограничение памяти). Политика по NIST SP 800-63B: от 10 до 128 символов, без требований к составу, но с запретом распространённых паролей (в том числе после отбрасывания цифр и знаков по краям, раскладки `йцукен`), почти однообразных строк и паролей, построенных из почты или имени. Для несуществующей почты выполняется такая же по времени проверка, чтобы ответ не выдавал наличие аккаунта.

## D-028. Оптимистичная блокировка: ETag и необязательный If-Match
**Контекст.** ТЗ требует ETag/`If-Match`. Обязательный `If-Match` на каждом обновлении усложняет клиентов там, где одновременная правка невозможна (собственный профиль).
**Решение.** Общие редактируемые ресурсы отдают `ETag` (версия по `updated_at`); обновление с `If-Match` при несовпадении версии получает 412 `precondition.failed`, строка блокируется `SELECT … FOR UPDATE` на время проверки. В фазе 2 это запросы доски «Ищу в команду». Для совместно редактируемых документов (данные шагов проекта, фаза 4) `If-Match` будет обязательным.

## D-029. Лимиты запросов с учётом NAT кампуса
**Контекст.** Студенты вуза часто выходят в интернет через один адрес; на вводном занятии сотня человек регистрируется и входит одновременно.
**Решение.** Лимиты по IP рассчитаны на аудиторию (вход — 120 сразу и 600 в час, регистрация — 100 и 300 в час, коды — 100 и 300 в час, восстановление — 40 и 120 в час). Перебор останавливают лимиты по аккаунту: 10 попыток пароля за 15 минут на адрес, 5 писем с кодом или ссылкой в час на адрес, 5 попыток на код. Лимиты — GCRA в Valkey, общие для всех экземпляров API; ответ 429 содержит `Retry-After`.

## D-030. Векторный поиск: pgvector без фиксированной размерности и точный перебор
**Контекст.** Вуз может сменить модель эмбеддингов (mock → локальная модель → облачная), а у моделей разная размерность. Индекс HNSW требует колонку фиксированной размерности.
**Решение.** `knowledge_chunks.embedding` — `vector` без размерности, рядом хранится `embedding_model`. Поиск фильтрует фрагменты по модели текущего запроса и упорядочивает точным перебором (`<=>`, косинусное расстояние); если эмбеддинги недоступны или фрагментов этой модели нет — полнотекстовый поиск по `tsvector` (конфигурация `simple`, подходит для казахского). При смене модели документы переиндексируются задачей `knowledge.index`.
**Последствия.** На масштабе базы знаний вуза (тысячи фрагментов) точный перебор занимает миллисекунды и не теряет точность; ANN-индекс по выражению с приведением к размерности — B-013, когда фрагментов станет больше ~100 тысяч.

## D-031. AI-шлюз: маршруты по функциям и цепочка резервных провайдеров
**Контекст.** ТЗ требует переключать провайдера конфигурацией, разные модели для разных задач и работу без внешних API.
**Решение.** Все вызовы моделей идут через `ai.Gateway`. Провайдеры реализуют интерфейс `llm.Provider` (Anthropic — официальный Go SDK, OpenAI-совместимый — vLLM/Ollama/LM Studio/OpenAI, детерминированный mock). Маршрут — список «провайдер[:модель]» для функции (`mentor`, `evaluation`, `generation`, `summary`, `embedding`): из настроек вуза (`tenant_ai_settings`), иначе из `QADAM_AI_ROUTES`, иначе `QADAM_AI_DEFAULT`. При ошибке, недоступности или отказе модели запрос уходит следующему провайдеру цепочки. Модели Claude по умолчанию: ментор — `claude-sonnet-5-5` (диалог, быстрый отклик), оценка и генерация документов — `claude-opus-5-5`, сводки — `claude-haiku-5-5`. Для моделей Opus включены серверные резервные модели API (`fallbacks: "default"`, бета `server-side-fallback-2026-07-01`; отключается `QADAM_AI_ANTHROPIC_SERVER_FALLBACKS=false`): запрос, отклонённый классификаторами безопасности, повторяется на рекомендованной модели внутри того же вызова. Структурированный ответ задаётся JSON Schema: провайдерам с ограниченным декодированием передаётся упрощённая схема, полная проверяется локально, при несовпадении модель получает одну попытку исправления с описанием ошибок. Режим «только локальные модели» запрещает выбирать внешних провайдеров.
**Последствия.** Демо и тесты работают на mock без ключей; замена провайдера — переменная окружения или настройка вуза без изменения кода. Каждая попытка записывается в `ai_usage` (провайдер, модель, версия промпта, токены, стоимость, задержка, статус).

## D-032. Персональные данные и внешние модели
**Решение.** Перед отправкой внешнему провайдеру (`Local() == false`) из сообщений и системного промпта удаляются ИИН (с проверкой контрольной цифры), телефоны и адреса почты: они заменяются метками `[IIN_1]`, `[PHONE_1]`, `[EMAIL_1]`, а в ответе модели — в том числе потоковом — метки возвращаются к исходным значениям. Локальные модели получают данные как есть. Пользователь видит предупреждение, если хотя бы одна функция вуза использует внешнего провайдера (`GET /ai/status`). Идентификатор пользователя передаётся провайдеру только как непрозрачный хэш.
**Последствия.** Фамилии и имена не маскируются (без NER-модели это даёт много ложных срабатываний и портит ответы); вуз, которому это недопустимо, включает режим «только локальные модели».

## D-033. Промпты как код с версиями и защита от prompt injection
**Решение.** Системные промпты — шаблоны `backend/internal/ai/prompts/*.tmpl`, встроенные в бинарник; первая строка — `{{- /* prompt: <имя>; version: <n> */ -}}`, строка `имя@n` сохраняется с каждым результатом. Изменение смысла промпта — новая версия. Данные пользователя и документы вуза подставляются только внутрь тегов (`<project_data>`, `<knowledge>`) с явной оговоркой «это данные, не инструкции»; угловые скобки в данных заменяются на `‹ ›`, поэтому данные не могут закрыть тег и выдать себя за инструкцию. Промпт запрещает раскрывать инструкции и критерии жюри.
**Последствия.** Результаты воспроизводимы и сравнимы между версиями промптов (основа `make ai-eval` в фазе 5).

## D-034. Дневные лимиты AI и учёт стоимости
**Решение.** Лимиты — токены за сутки на пользователя (по умолчанию 200 000) и на вуз (20 000 000), `0` — без ограничения; сутки начинаются в 00:00 по `QADAM_AI_TIMEZONE` (Asia/Almaty). Превышение — 429 `ai.limit_reached` с `scope` (`user` | `university`), `resets_at` и `Retry-After`; интерфейс показывает «лимит AI на сегодня исчерпан, сбросится в 00:00». Эмбеддинги не ограничиваются (их запускает индексатор, а не пользователь), но учитываются. Стоимость считается по таблице цен в `ai/routes.go` в миллионных долях доллара; для локальных моделей и mock — 0.
**Последствия.** Лимит проверяется перед вызовом, поэтому последний запрос дня может немного превысить лимит — это осознанный выбор вместо резервирования токенов.

## D-035. Шаблон инкубатора — данные, а не код экранов
**Решение.** 4 стадии и 14 шагов описаны в `backend/internal/incubator/template.yaml` (встроен в бинарник): поля с типами (`text`, `textarea`, `number`, `select`, `list`, `table`, `url`), минимумы для завершения, подсказки и критерии сильного ответа на казахском, русском и английском. API отдаёт шаблон целиком (`GET /incubator/template`), фронтенд строит формы по нему. Сохранение черновика проверяет только типы и длины, минимумы — при завершении шага. Критерии привязаны к полям: по ним работает и AI-проверка, и чек-лист «что усилить».
**Последствия.** Изменение шагов не требует правки фронтенда; настройка шаблона вузом (B-019) сводится к хранению YAML/JSON в БД.

## D-036. Совместное редактирование шага: версия, обязательный If-Match и слияние по полям
**Контекст.** Над шагом одновременно работают несколько студентов; полноценный CRDT ТЗ не требует.
**Решение.** У шага есть версия (ETag `"<n>"`), каждое сохранение (автосохранение отправляет только изменённые поля) требует `If-Match` (без него — 428 `precondition.required`, с устаревшей версией — 412). Клиент при 412 загружает свежую версию и сливает изменения по полям (база — версия, с которой начал, «их» — сервер, «мои» — локальные); при пересечении по одному полю показывает выбор. История — ревизия на каждое изменённое поле; автосохранения одного автора в течение 3 минут сворачиваются в одну ревизию (иначе история состояла бы из сотен шагов по 1,2 с). Откат — новая ревизия со старым значением.
**Последствия.** Если автор очищает поле в пределах 3 минут после ввода, промежуточный текст не сохраняется в истории — это осознанный компромисс читаемости истории.

## D-037. Присутствие — опрос, а не постоянное соединение
**Решение.** Открытая страница проекта раз в 15 секунд сообщает, на каком шаге пользователь (`POST /projects/{id}/presence`); Valkey хранит отметки в хэше проекта (окно 45 секунд). Ответ содержит, кто в проекте, и текущие версии всех шагов — клиент тихо перезагружает шаг, изменённый другими.
**Последствия.** Никаких долгоживущих соединений через прокси вуза и балансировщики; задержка появления чужих правок — до 15 секунд, что достаточно для учебной командной работы.

## D-038. Диалоги с ментором
**Решение.** Диалоги хранит модуль `ai` (`ai_conversations`, `ai_messages`) с предметом «шаг проекта»; инкубатор передаёт контекст: карточку проекта, ответы текущего шага и все заполненные поля других шагов (JSON внутри `<project_data>`), критерии шага и до трёх фрагментов базы знаний вуза (источники показываются под ответом). Вопрос сохраняется после того, как модель начала отвечать (отказ по лимиту не оставляет вопрос без ответа); ответ сохраняется и при обрыве соединения — со статусом `cancelled`. Язык ответа — язык интерфейса (`Accept-Language`), иначе язык вуза. Предложения формулировок модель оформляет тегом `<suggestion field="…">`, интерфейс показывает кнопку «Применить в поле» (ревизия с источником `mentor`). Спрашивать ментора может только команда; режим «соавтор» разрешается настройкой вуза.

## D-039. Генерация материалов
**Решение.** One-pager, питч-дек и паспорт стартапа: тексты пишет модель по данным проекта (промпт запрещает выдумывать факты; mock собирает тексты из ответов команды), документы рендерятся из HTML-шаблонов в PDF через Gotenberg (Chromium), PPTX питч-дека — собственный генератор Office Open XML (16:9, без внешних зависимостей; открывается в PowerPoint, LibreOffice, Google Slides), QR-код паспорта — `rsc.io/qr` в SVG. Генерация — задача River; карточка проекта и бренд вуза фиксируются в момент запроса. Файлы приватные и отдаются только через `/projects/{id}/materials/{id}/content` после проверки доступа к проекту.

## D-040. Доступ к проекту
**Решение.** Команда (владелец и участники) редактирует и спрашивает ментора; научный руководитель (участник вуза с ролью `supervisor`, назначается владельцем или innovation manager) читает, комментирует и одобряет шаги, в том числе не дотягивающие до минимума, с обязательным комментарием; innovation manager и администратор вуза видят все проекты, одобряют и модерируют; руководство вуза — только читает. Для остальных проект не существует (404, а не 403). Архивный проект доступен только для чтения. Владелец не может покинуть проект, не передав его.

## D-041. AI-оценка: баллы ставит модель, итог считает сервер
**Решение.** Модель возвращает по каждому критерию рубрики балл 0–10 с обоснованием, red flags, 3–5 гипотез, эксперименты на 7 дней и рекомендации (JSON Schema с перечислением ключей рубрики; ответ, не покрывающий рубрику, отклоняется). Итог 0–100 = Σ вес × балл / 10 и уровень готовности (`idea` < 35 ≤ `validated_problem` < 55 ≤ `mvp_ready` < 75 ≤ `investment_ready`) считает сервер, поэтому итог всегда согласован с весами и корректировками. С оценкой хранится снимок весов: смена рубрики вузом не меняет прошлые оценки. Оценка идёт фоном (River), одна на проект одновременно, не больше 5 в сутки. Научный руководитель или innovation manager может изменить балл критерия с обязательным комментарием: AI-балл, итог AI и история корректировок остаются видны. Отчёт и PDF прямо называют оценку рекомендацией AI и указывают провайдера, модель и версию промпта.

## D-042. Проверка промпта оценки: `make ai-eval`
**Решение.** Золотые проекты (`internal/evaluation/testdata/cases.json`: пустой, расплывчатый, с подтверждённой проблемой, полный демо-проект, попытка подменить инструкции, проект на казахском) с ожиданиями: диапазон итога, уровень, язык текстов, не все десятки при инъекции. `make ai-eval` прогоняет их на модели, выбранной как в платформе (`QADAM_AI_*`, маршрут функции `evaluation`), и печатает таблицу; без настроек проверяется детерминированный mock, и юнит-тест в CI прогоняет те же кейсы.
**Последствия.** Изменение промпта или модели проверяется до выкладки одной командой; при новой версии промпта ожидания при необходимости уточняются в кейсах.

## D-043. Видимость и модерация страниц витрины
**Решение.** Страница проекта на витрине — отдельная сущность (`showcase_entries`), которую команда собирает из ответов инкубатора (до первого сохранения API отдаёт предзаполненный вариант) и правит сама. Видимость `university` — для участников вуза, публикуется сразу; `public` — для всех, после одобрения innovation manager. Пока страница ждёт решения или отклонена, она остаётся видна внутри вуза (`published_at` задан), наружу — только при статусе `published`. Отклонение требует комментария; модератор может снять с публичной витрины и уже опубликованную страницу. Правки опубликованной публичной страницы видны сразу, без повторной модерации (иначе каждая опечатка уводила бы проект с витрины); модерация повторяется при переходе `university → public` и после отклонения. Видимость проекта (`private` / `university` / `public`) следует за страницей. Юнит-экономика и технологии на страницу не попадают вовсе, поэтому флаг «скрыть чувствительные детали» витрину не затрагивает.
**Последствия.** Злоупотребление правками после одобрения ловится постфактум: модератор видит все публичные страницы и может их отклонить.

## D-044. Национальная витрина — через RLS, без копирования данных
**Решение.** Политика `showcase_entries` разрешает читать опубликованные публичные страницы из контекста любого вуза; запись — только своему вузу. Страница хранит всё, что нужно карточке и публичной странице (факультет, команду с аватарами, балл и уровень последней оценки на момент сохранения), поэтому национальный каталог не читает чужие таблицы проектов и пользователей. Обложки и аватары — публичные файлы. Ссылка карточки абсолютная: страница живёт на сайте своего вуза (основной домен, `PUBLIC_URL` для вуза по умолчанию или `<slug>.<базовый домен>`).
**Последствия.** Балл на витрине обновляется при сохранении страницы, а не при каждой новой оценке — команда сама решает, когда показать новый результат.

## D-045. SEO без SSR: API подставляет метаданные в оболочку SPA
**Контекст.** Нужны корректные `<title>`, description, Open Graph и JSON-LD для `/showcase/*` и превью ссылок, но фронтенд — SPA на Vite.
**Решение.** Nginx отправляет `/showcase`, `/showcase/{slug}`, `/sitemap.xml` и `/robots.txt` в API. API берёт собранный `index.html` веб-клиента (`QADAM_APP_SHELL_URL`; копия перепроверяется на каждой странице условным запросом с ETag — ответ 304, пока сборка та же, а новая подхватывается сразу, иначе страница ссылалась бы на удалённые скрипты прошлой сборки; при недоступности — последняя копия или минимальная страница), подставляет язык, заголовок, описание, canonical, OG/Twitter-теги, JSON-LD (`CreativeWork` для проекта, `CollectionPage` со списком для каталога) и `<noscript>` с текстом страницы, после чего React монтируется как обычно. Страницы только для участников и несуществующие выглядят одинаково: 404 с `noindex` (веб-клиент всё равно откроет страницу участнику). Если API недоступен, Nginx отдаёт обычный `index.html`. `robots.txt` закрывает кабинет и страницы входа, `sitemap.xml` перечисляет публичные страницы вуза.
**Альтернативы.** SSR (Next.js/Remix) — второй рантайм в on-prem-установке; пререндер headless-браузером — тяжело и медленно для каждой правки.

## D-046. OG-картинки — скриншот HTML через Gotenberg с кэшем по содержимому
**Решение.** Картинка 1200×630 рисуется из HTML-шаблона (бренд вуза, название, слоган, стадия, отрасль, балл — если команда его показывает, обложка или «маршрут» стадий) скриншотом Chromium в Gotenberg и хранится как публичный файл вместе с хэшем показанных данных; следующий запрос отдаёт сохранённую картинку, пока данные не изменились. В ссылке на картинку — версия страницы, чтобы соцсети перечитали её после правки. Без Gotenberg отдаётся простая картинка в цветах вуза с обложкой (не сохраняется).

## D-047. Запросы на контакт: команда не раскрывает адреса
**Решение.** Партнёр заполняет форму на публичной странице; адреса команды ему не показываются. По настройке вуза (`contact_moderation`, по умолчанию включена) запрос сначала видит innovation manager и пересылает его команде или отклоняет; без модерации он сразу уходит владельцу и участникам письмом (с адресом партнёра для ответа) и появляется в списке запросов проекта. Защита от спама: скрытое поле-ловушка (заполненное — «принято», но не сохраняется), не больше 5 запросов в час с адреса и 20 в сутки на проект, команда может закрыть форму.

## D-048. Поиск по витрине
**Решение.** Полнотекстовый поиск по `tsvector` с конфигурацией `simple` (без стемминга: для казахского в PostgreSQL нет словаря, а единая конфигурация работает одинаково на трёх языках); слова запроса превращаются в префиксные термы (`агро:* & скан:*`), в запрос попадают только буквы и цифры. Текст для поиска собирает приложение из названия, слогана, разделов и тегов. Сортировка — по дате публикации (курсорная пагинация), фильтры — отрасль, стадия, факультет, год, теги («технологии»), что нужно проекту.

## D-049. Визуальный стиль — как у сайта университета (mooc.kaztbu.edu.kz)
**Контекст.** Заказчик попросил, чтобы платформа выглядела как его сайт открытых онлайн-курсов. Стиль сайта задан набором токенов `--kz-*`: тёмно-синий «ink» #102945 и navy #001E40, бирюзовый акцент #067A75 (яркий #09BAB2, мятный #83DCD5), зеленовато-серые нейтральные (#191C1D, #5C6866, #DFE6E4, фон #F4F7F6), карточки со скруглением 14 px, прямоугольные кнопки и поля, заглавные надписи с разрядкой, заголовки Literata, текст Google Sans.
**Решение.** Перенести стиль в токены дизайн-системы, а не копировать CSS: primary — бирюзовая шкала (700 = #067A75, белая надпись 5,2 : 1; при наведении кнопка становится тёмно-синей, как на сайте), новые токены `ink` (заголовки и тёмные кнопки), `deep-*` (тёмные панели), `radius-control` = 0 и `radius-card` = 14 px, `tracking-caps/label/kicker`; утилиты `panel-ink`, `panel-deep`, `font-figures`; компонент `Kicker` (черта и подпись капсом над заголовком секции). Шрифты — Google Sans и Literata (обе OFL, `@fontsource-variable`, self-hosted; казахский алфавит проверен `fonts:check`); крупные числа набираются Google Sans, как статистика сайта. Публичная шапка белая с подчёркиванием активного пункта, подвал и hero — тёмно-синие, вход — тёмная панель слева и форма на белом. Тёмная тема сохранена и перекрашена в глубокий сине-бирюзовый. Цвет вуза (`primary_color`) по-прежнему используется для OG-картинок и меток вуза в национальной витрине; КазУТБ в демо-данных получает #067A75.
**Палитра целиком.** Все шкалы привязаны к цветам сайта: ступени, которые сайт использует, равны его значениям — primary (#067A75 = 700, #0A9D96, #09BAB2, #5FD6CD, #83DCD5, тона #D5EBE7 / #E3F4F2 / #F0F8F7), ink и deep (#102945, #2C5A86, #0D1F2C, #001E40, #082834, #0E3A3F, #14696D), success (#1B7A4A / #3FB57A, тон #E3F3EA), warning (#8A5A00, тон #FBF0D6), danger (#BA1A1A, тон #FBE5E3), info (#2C5A86, тон #E8EEF5), gold (#B07A00 → #E2B53E), новая copper (#A4531F → #D9853F); остальные ступени достроены в OKLCH. Как на сайте, мягкие бейджи и плашки — тон 700 на подложке 100 (4,6–6,2 : 1, поэтому текст в них без прозрачности). ## D-050. Первый экран публичных страниц рисует сервер
**Контекст.** Lighthouse на телефоне (Slow 4G, CPU ×4) давал публичным страницам 67–72: SPA ничего не рисует, пока не загрузит JS (~230 КБ gzip), переводы и чанк маршрута — при реальном троттлинге первая отрисовка около 9 с.
**Решение.** Для `/`, `/showcase` и `/showcase/{slug}` API (тот же путь, что D-045) вставляет перед `#root` шапку и первый экран страницы (`#boot`): hero лендинга, hero каталога, обложку и заголовок проекта — разметкой и классами компонентов клиента, на языке, который клиент выберет сам (cookie `qadam_locale`, которую ставит клиент, затем `Accept-Language`, затем казахский; ответ с `Vary: Accept-Language, Cookie`). `theme-init.js` до отрисовки помечает язык клиента (`html[data-locale]`): первый экран на другом языке не показывается, а при совпадении приложение рендерится скрытым под ним и убирает его, когда маршрут загружен, в `main` есть содержимое и запросы данных завершились (`src/app/boot.ts`). Тесты сверяют тексты первого экрана с переводами клиента и проверяют, что каждый его класс есть в исходниках клиента (иначе Tailwind не создаст правило).
**Результат.** При реальном троттлинге первая отрисовка 8,8 → 2,6 с, Speed Index 8,7 → 6,1 с; подмена на приложение не видна (раскадровка). Балл Lighthouse на телефоне не вырос (63–72): LCP засчитывается по заголовку, который React создаёт заново, а TBT теперь учитывает выполнение JS после первой отрисовки. Дальше — B-010.
**Альтернативы.** SSR/гидратация (второй рантайм on-prem, отклонено в D-045); статичный скелет без текста (не даёт содержимого раньше JS).

## D-054. Compose: базовый файл, файл разработки и проверки продакшна
**Контекст.** `deploy/docker-compose.yml` публиковал на всех интерфейсах Postgres, Valkey без пароля, MinIO (приложение ходило в него корневыми ключами), Gotenberg, ClamAV, Mailpit и API в обход Nginx; установка с `QADAM_ENV=production` без SMTP запускалась и отправляла коды входа в открытый Mailpit, письма уходили от `no-reply@qadam.kz` (аудит В-4, В-5, Н-56).
**Решение.** Базовый `deploy/docker-compose.yml` поднимает все службы и публикует только web. `deploy/docker-compose.dev.yml` добавляет порты служб на `127.0.0.1` (`DEV_BIND`, номера из D-013) и Mailpit; `make dev`, `make infra` и CI складывают оба файла, `make compose-check` проверяет оба варианта. Valkey — с `requirepass` (`VALKEY_PASSWORD` → `QADAM_VALKEY_PASSWORD`), health check сверяет ответ `PONG`. Корневые ключи MinIO (`MINIO_ROOT_USER`/`MINIO_ROOT_PASSWORD`) видят только `minio` и одноразовый `minio-init` (`cgr.dev/chainguard/minio-client`, закреплён по digest, как в D-008): он при каждом старте создаёт бакет, политику `qadam-app` (чтение, запись и удаление объектов одного бакета) и пользователя приложения `S3_ACCESS_KEY`. Через compose передаются `SMTP_*`, `S3_BUCKET`, `S3_USE_SSL`, `OTEL_*`. В продакшне конфигурация отказывается стартовать с `QADAM_SMTP_HOST=mailpit`, без `QADAM_SMTP_FROM` (адрес `no-reply@qadam.kz` подставляется только вне продакшна), с `QADAM_SMTP_TLS=none` при логине SMTP, без пароля Valkey и с паролями БД, Valkey и S3, содержащими `dev` (как значения `.env.example`). Пароль в URL БД не обязателен (сертификат, `.pgpass`), TLS не обязателен для релея без логина.
**Последствия.** Порты разработки прежние, но только на этой машине. Существующему `.env` нужны `VALKEY_PASSWORD`, `MINIO_ROOT_*` (прежние значения `S3_*`, чтобы данные MinIO остались с теми же корневыми ключами) и новая пара `S3_*` для пользователя приложения. Базовый файл — ещё не prod-конфигурация: TLS, резервные копии, мониторинг и хранение секретов — фаза 12.

## D-055. Адрес клиента и журналы за Nginx
**Контекст.** Доверенными прокси считались все частные сети, Nginx дописывал присланный клиентом `X-Forwarded-For`, а API шёл влево мимо доверенных адресов: клиент из кампусной сети выбирал себе IP, обходил лимиты и подменял адрес в аудите (аудит С-6). Адрес контейнера web в сети compose заранее неизвестен. Журнал Nginx хранил полную строку запроса с токенами из писем и кодами SSO (С-7).
**Решение.** Nginx перезаписывает `X-Forwarded-For` своим `$remote_addr`; API доверяет одному хопу и берёт только последнюю запись заголовка. Список `QADAM_HTTP_TRUSTED_PROXIES` остаётся и значит «кто может быть Nginx». TLS-прокси перед Nginx (фаза 12) подключается модулем realip Nginx (`set_real_ip_from`, `real_ip_header X-Forwarded-For`), а не вторым доверенным хопом в API. Журнал доступа Nginx пишет путь без query-строки и без `Referer` (он повторяет ссылку со страницы), зато с `$request_id`, общим с журналом API; API и так пишет только путь, спаны OpenTelemetry — только `url.path`.
**Последствия.** Подделать адрес можно только изнутри сети compose, куда API наружу не опубликован. Без realip за TLS-прокси все клиенты станут одним адресом. В журнал ошибок Nginx при недоступном API строка запроса попадает целиком — это одноразовый короткоживущий код SSO.

## D-056. Роль базы данных проверяется при старте
**Контекст.** `QADAM_DATABASE_MIGRATE_URL` по умолчанию равен `QADAM_DATABASE_URL`, и ничто не мешало указать владельца схемы или суперпользователя для API: RLS молча переставал работать (аудит С-11).
**Решение.** `db.Connect` (API, worker, seed) после подключения проверяет `current_user`: не суперпользователь, без BYPASSRLS и не владеет таблицами — ни сам, ни через членство в роли, которая это может (`pg_has_role … 'MEMBER'`, член может сделать `SET ROLE`). Иначе процесс не стартует и объясняет, что указать. Миграции подключаются владельцем, тесты (`testpg`) — ролью `qadam_app`.
**Последствия.** Таблица, созданная ролью приложения, а не миграцией, остановит старт — так и задумано.

## D-057. Таймауты и лимит тела — по маршрутам из openapi.yaml
**Контекст.** Заголовок `Accept: text/event-stream` снимал таймаут с любого эндпоинта, `Content-Type: multipart/form-data` поднимал лимит тела любого запроса до 26 МБ; у сервера не было `WriteTimeout` (аудит Н-8).
**Решение.** При сборке API операции с ответом `text/event-stream` и с телом `multipart/form-data` читаются из встроенного `openapi.yaml` и сопоставляются по методу и шаблону пути: таймаут контекста снимается только с первых, большой лимит тела действует только на вторые. Сервер получил `QADAM_HTTP_WRITE_TIMEOUT` (5 минут, не меньше таймаута запроса). Поток SSE снимает дедлайн чтения (по нему net/http отменяет контекст запроса) и ставит дедлайн записи на каждое событие (минута).
**Последствия.** Новая потоковая или загрузочная операция получает нужные правила из спецификации, без ручного списка.

## D-058. Размер страницы вне контракта — ошибка
**Контекст.** `openapi.yaml` объявляет `limit` от 1 до 100 (поиск людей — до 50), а сервер молча ограничивал любое значение (аудит Н-55).
**Решение.** `limit` вне диапазона — `400 request.invalid_limit` с параметрами `min` и `max`, как `request.invalid_cursor` (это параметр запроса, а не поле формы, поэтому не 422). Значения по умолчанию у операций прежние. Все вызовы веб-клиента запрашивают не больше 100.
**Последствия.** Сторонний клиент с `limit=500` получит понятную ошибку вместо неполной страницы.

## D-059. Импорт XLSX до релиза excelize с исправлениями
**Контекст.** В excelize v2.11.0 (последний релиз) четыре уязвимости на испорченных файлах (GO-2026-6684, -6685, -6688, -6689); исправления есть только в основной ветке (аудит С-14).
**Решение.** Остаёмся на релизе и ограничиваем разбор: открывается только ZIP (зашифрованная книга — контейнер OLE, её расшифровка и падает, и выделяет память без предела), лист читается итератором строк вместо `GetRows` с потолком в 300 000 просмотренных строк (строка с огромным номером заставляла перебирать все номера до неё), заголовок — не шире 50 столбцов (`import.too_many_columns`), ячейки правее заголовка не хранятся, формулы не вычисляются, паника внутри excelize — «файл не читается». Ограничения распаковки (64 МБ, 32 МБ на XML-часть) прежние.
**Последствия.** Переход на релиз с исправлениями — B-024; govulncheck продолжит показывать эти уязвимости по символам, хотя пути к ним закрыты.

## D-061. Фоновые задачи AI не остаются «в работе» навсегда
**Контекст.** Последняя попытка задачи River часто падает именно потому, что истёк её таймаут; запись провала на истёкшем контексте не проходила, и оценка оставалась `running` — следующая оценка проекта получала 409 навсегда (аудит В-3, Н-17, С-17). Падение или выкладка worker и задачи, которые River отбросил, дают то же.
**Решение.** Провал последней попытки пишется на отдельном контексте (`jobs.Detach`: `context.WithoutCancel` и 15 секунд). Вызов модели укладывается в таймаут задачи с запасом на запись результата (оценка — 9 из 10 минут, материалы — 3 из 5). Одна периодическая задача `platform.fail_stale` (раз в 10 минут) запускает «жнецов» модулей: каждый модуль переводит в `failed` свои записи, не менявшиеся дольше худшего времени всех попыток (оценки — 45 минут, материалы — 30 минут, документы базы знаний — 5 часов), с кодами `evaluation.timed_out`, `incubator.material_timed_out`, `knowledge.index_failed`; заодно удаляются истёкшие резервы токенов. Обновления статусов условные (`WHERE status IN (…)`), поэтому поздно закончившаяся задача не перезапишет уже снятую запись. Индексация документа получает таймаут по числу фрагментов (минута плюс 30 секунд на пакет из 32, не больше 45 минут — меньше часа, после которого River считает задачу зависшей); документ, не проиндексированный трижды, почасовая переиндексация больше не берёт — администратор загружает его заново. Фрагменты одного документа — векторы одной модели и размерности: смена провайдера посреди документа отменяет попытку. Проект хранит 20 последних готовых материалов, более старые удаляются вместе с файлами; антивирус и загрузка в S3 идут вне транзакции.
**Последствия.** Пользователь узнаёт о сбое не позже чем через худшее время задачи и 10 минут и может повторить запрос. Если очередь стоит дольше окна (worker выключен на часы), ожидающая оценка тоже будет снята — её задача, придя позже, увидит `failed` и ничего не сделает.

## D-062. OpenAI-совместимый сервер внешний, пока не доказано обратное
**Контекст.** `OPENAI_LOCAL=true` по умолчанию считал локальным любой сервер: направив `OPENAI_BASE_URL` на api.openai.com и забыв флаг, вуз отправлял персональные данные за рубеж без маскирования и предупреждения (аудит С-10, раздел 7 ТЗ).
**Решение.** `QADAM_AI_OPENAI_LOCAL` принимает `auto` (по умолчанию), `true` или `false`. При `auto` локальным считается только адрес, который не может быть в интернете: `localhost`, loopback, частный или link-local IP, `host.docker.internal` и имя без точки (сервис Docker Compose, например `ollama`). `true` объявляет локальным любой адрес, `false` — внешним даже частный (прокси вроде LiteLLM, пересылающий запросы в облако). О каждом внешнем провайдере API и worker пишут предупреждение в журнал при старте; для OpenAI-совместимого — с адресом и подсказкой про флаг. Предупреждение пользователям (`GET /ai/status`) учитывает и эмбеддинги: вопрос ментору тоже эмбеддится для поиска по базе знаний (Н-27); оно показывается и на странице оценки, и у AI-проверки шага.
**Последствия.** Установка с локальной моделью по имени сервиса или частному адресу работает как раньше; локальный сервер с публичным именем (`llm.kaztbu.edu.kz`) требует явного `OPENAI_LOCAL=true` — ошибка в эту сторону лишь маскирует данные без нужды.

## D-063. Резерв токенов вместо проверки перед вызовом; эмбеддинги вне лимитов
**Контекст.** D-034 проверял лимит до вызова и не учитывал идущие вызовы: три десятка параллельных запросов превышали лимит в разы (аудит Н-21). Токены эмбеддингов шли в дневной лимит вуза — большая переиндексация могла оставить студентов без ментора (С-17).
**Решение.** Перед вызовом шлюз под advisory-блокировкой вуза считает потраченное за сутки плюс резервы идущих вызовов и, если лимит не достигнут, резервирует для вызова его максимум (вход примерно по 4 символа на токен плюс `max_tokens`) в `ai_reservations`; резерв снимается, когда вызов записан в `ai_usage`, а резерв упавшего процесса истекает через 15 минут. Лимит можно превысить не больше чем на один вызов. Эмбеддинги (индексатор и вопросы к базе знаний) по-прежнему записываются в `ai_usage`, но в лимиты пользователя и вуза не входят и не показываются в «использовано сегодня». Ответ со схемой, обрезанный по `max_tokens`, повторяется с вдвое большим лимитом (не больше 32 000) вместо «исправления» с тем же лимитом; обрезанный дважды — понятная ошибка `ai.invalid_output` с кодом `truncated` в учёте (Н-24).
**Последствия.** Каждый вызов модели — две короткие записи в БД (резерв и его снятие); последовательная работа одного пользователя не меняется.

## D-064. Порог релевантности базы знаний и mock-эмбеддинги без шума
**Контекст.** Поиск всегда подставлял три фрагмента, даже совсем не относящиеся к вопросу (аудит Н-28); векторы mock (256 корзин, служебные слова) давали несвязанным текстам такую же близость, как связанным.
**Решение.** Фрагменты с косинусной близостью ниже порога модели не возвращаются: `QADAM_AI_EMBEDDING_MIN_SIMILARITY` (по умолчанию 0,3, подбирается под модель эмбеддингов вуза), для mock — 0,06. Если близких фрагментов нет, остаётся полнотекстовый поиск, требующий всех слов вопроса, — обычно и он пуст, и ментор отвечает без источников. Сравниваются только векторы той же размерности. Mock-эмбеддинги — 1024 корзины без служебных слов на трёх языках, модель `mock-hash-1024`: смена имени переиндексирует документы почасовой задачей (D-030). Файл базы знаний проверяется антивирусом до разбора, извлечённый текст ограничен 4 МБ (`knowledge.text_too_long`).
**Последствия.** На демо-установке после обновления документы переиндексируются при первом запуске worker; до этого поиск идёт по тексту.

## D-065. Харнесс AI-оценки идёт через шлюз и проверяет red flags и порядок проектов
**Контекст.** Харнесс D-042 вызывал провайдера напрямую и не заметил, что оценка разбирала сырой текст ответа, а не проверенный шлюзом JSON: локальная модель, обернувшая JSON в блок кода, проходила проверку схемы и роняла разбор (аудит С-16). Кейсов было 6.
**Решение.** Шлюз отдаёт для вызова со схемой сам JSON-значение (`schema.Extract`), разбор оценки тоже его извлекает. Worker и харнесс вызывают одну функцию `evaluation.Evaluate` (промпт, схема, шлюз, разбор); харнесс работает со шлюзом без БД (настройки по умолчанию, без лимитов и учёта). 22 золотых кейса: кроме диапазонов итога, уровня и языка — ожидаемые red flags (минимум, высокая важность, упоминание: «LTV|CAC|юнит», «конкурент» и т. п.) и порядок: сильный проект выше его версий с одной слабостью, демо-проекты по степени готовности. Без настроек mock прогоняется дважды — как есть и с JSON в блоке кода Markdown. `go run ./cmd/ai-eval` работает без сети и БД; тот же набор — юнит-тест, а отдельный тест проверяет, что харнесс ловит «плохого» рецензента.
**Последствия.** Ожидания кейсов сформулированы для строгого эксперта, а не под mock: на реальной модели отдельные кейсы могут потребовать уточнения при смене версии промпта.

## D-066. Сессия только после подтверждения почты
**Контекст.** Аудит В-1 и С-2: регистрация сразу давала активное членство и сессию, поэтому можно было занять чужой адрес вуза (`rector@…`) и выглядеть его владельцем, а потом получить аккаунт настоящего владельца через SSO; регистрация на существующую почту подбирала пароль в обход блокировки входа.
**Решение.** Регистрация нового аккаунта создаёт пользователя, пароль и членство студента, отправляет письмо и отвечает 202 `{verification_sent: true}` — без сессии. Вход паролем на неподтверждённую почту — 403 `auth.email_unverified` без сессии; письмо можно отправить ещё раз без входа (`POST /auth/email/resend` с адресом: ответ всегда 202, не больше 5 писем в час на адрес). Ссылка из письма подтверждает почту и сразу выполняет вход (`POST /auth/email/verify` → `Session`), поэтому ведёт прямо в онбординг. Почту подтверждает всё, что доказывает доступ к ящику: код из письма, сброс пароля, принятие приглашения, SSO с `email_verified=true`, первый пароль по коду (D-071 «Коды входа, первый пароль и ответы о почте»). Регистрация на адрес, чей аккаунт ещё не подтверждён, забирает его: заменяются пароль, имя и язык, отзываются сессии и одноразовые ссылки во всех вузах (кроме приглашений вуза), уходит новое письмо — аккаунт достаётся тому, кто владеет ящиком; ответ тот же, что у нового аккаунта. Подтверждённый аккаунт по-прежнему вступает в вуз с верным паролем (D-024, ответ 201 с сессией), но попытки идут в тот же лимит по адресу, что вход, а неверный пароль пишется в аудит как `auth.login_failed`. Сессии аккаунтов только с паролем и неподтверждённой почтой (открытые до этого решения) завершаются при следующем обновлении. Письмо подтверждения предупреждает, что ссылка выполняет вход и её не нужно открывать, если вы не регистрировались.
**Последствия.** Демо-аккаунты сидов подтверждены и входят как раньше. E2E-сценарии регистрации открывают ссылку из письма в Mailpit. Остаточный риск: владелец ящика, открывший ссылку чужой регистрации, входит в аккаунт с паролем, который задал другой, — поэтому письмо прямо просит не открывать ссылку, а повторная регистрация или сброс пароля заменяют пароль.

## D-067. SSO вуза привязывается только к аккаунтам своего вуза
**Контекст.** Аудит С-5: провайдер любого вуза, подтвердивший почту, привязывался к глобальному аккаунту с этой почтой; администратор IdP вуза B мог войти в аккаунт пользователя вуза A.
**Решение.** Первый вход через SSO привязывается к существующему аккаунту (при `email_verified=true`, D-024), только если аккаунт уже участник этого вуза или его адрес на одном из почтовых доменов вуза (`tenant_settings.email_domains`; пустой список доменов не разрешает ничего); иначе — `/login?error=auth.sso_link_denied`. Привязка к аккаунту с неподтверждённой почтой удаляет его пароль, отзывает все его сессии во всех вузах и подтверждает почту.
**Последствия.** Участник нескольких вузов входит в «чужой» вуз паролем или кодом; вуз без почтовых доменов привязывает SSO только к своим участникам.

## D-068. Смена учётных данных отзывает сессии во всех вузах
**Контекст.** Аудит С-4: пароль общий для всех вузов аккаунта (D-007), а сброс, смена пароля и «выйти везде» отзывали сессии под RLS текущего вуза.
**Решение.** Эти операции (и захват неподтверждённого аккаунта, и привязка SSO к нему) отзывают сессии аккаунта во всех вузах одним запросом в системной области (`db.WithSystem`), отфильтрованным по `user_id`, в собственной маленькой транзакции — внутри транзакции изменения она становится её точкой сохранения и фиксируется вместе с ним. Отозванные сессии попадают в deny-list Valkey. Блокировка участника администратором по-прежнему завершает сессии только в своём вузе.
**Последствия.** Системная область используется осознанно и узко: только эти два запроса (сессии и одноразовые токены аккаунта).

## D-069. Неизвестный хост — не вуз по умолчанию
**Контекст.** Аудит Н-4 и Н-5: любой неизвестный `Host` (в том числе прямо на `:8080`) обслуживался как вуз по умолчанию, порт в ссылках писем брался из заголовка, кэш определения вуза рос без ограничения.
**Решение.** Уточняет D-025: вуз по умолчанию обслуживается только на базовом домене, хосте `QADAM_APP_PUBLIC_URL` и `localhost`; прочие неизвестные хосты — 404 `tenant.not_found`. Адрес вуза для ссылок строится из хранимого домена или поддомена `<slug>.<базовый домен>` со схемой и портом `PUBLIC_URL` (для вуза по умолчанию — сам `PUBLIC_URL`), а не из написания и порта запроса; так же строятся адреса витрины. Кэш ограничен 1024 хостами, при заполнении сначала вытесняются просроченные записи.

## D-070. Импорт: коды без учёта регистра, роли студентов и сотрудников, лимит приглашений
**Контекст.** Аудит Н-9.
**Решение.** Коды факультетов, кафедр и групп — `citext` (миграция 00011): уникальность и поиск по коду без учёта регистра, `IT` и `it` — один факультет. Уточняет D-026: файл назначает только роли `student`, `supervisor`, `mentor`, `jury`; `innovation_manager` и `partner`, как и административные, назначаются в интерфейсе. Приглашения импорта расходуют дневной лимит вуза (5000 писем в сутки, «всё или ничего»: при превышении импорт не применяется, 429 `import.too_many_invitations`).
**Последствия.** Вуз, у которого уже есть коды, различающиеся только регистром, объединяет их до миграции 00011.

## D-071. Коды входа, первый пароль и ответы о почте
**Контекст.** Аудит Н-1, Н-2, Н-3.
**Решение.** Уточняет D-029: каждая попытка ввести код входа расходует лимит аккаунта по всем его кодам (10 сразу, затем 10 в сутки; успешный вход сбрасывает), неверный код пишется в аудит (`auth.login_code_failed`). Аккаунт без пароля (созданный через SSO) задаёт первый пароль только с кодом из письма (`code` в `PUT /auth/password`; без него — 403 `auth.reauth_required`): сессии недостаточно, иначе украденная сессия превратилась бы в постоянный пароль. Ответы на запрос кода, ссылки сброса и письма подтверждения приходят не раньше чем через 300 мс после проверки лимитов, чтобы время ответа не выдавало, есть ли аккаунт.

## D-072. Каталог участников и структура вуза — для своих
**Контекст.** Аудит Н-10.
**Решение.** Поиск участников (`GET /people`) доступен ролям вуза; участник только с ролью `partner` получает 403. Факультеты и группы читают только вошедшие участники (форме регистрации они не нужны, онбординг и администрирование выполняются после входа). Краткие описания пользователей по id (авторы, упоминания, команды) отдаются только для участников текущего вуза. Последний администратор вуза защищён блокировкой строк администраторов (аудит Н-6); смена ролей и блокировка аннулируют токены внутри той же транзакции.

## D-073. Сборка фронтенда: без source maps, иконки одним файлом, данные страницы с маршрутом
**Контекст.** Аудит (Н-52): source maps публиковались вместе со сборкой (исходники кабинета доступны любому по адресу `*.js.map`), каждая иконка lucide была отдельным чанком (главная грузила 45 JS-файлов), набор иллюстраций попадал во входной бандл через страницу 404, а страница шага ждала шаблон, затем шаг, и показывала скелетон при каждом переключении.
**Решение.** Production-сборка без source maps (`build.sourcemap: false`); отладочная сборка с `QADAM_SOURCEMAP=hidden` получает их без ссылки в коде — файлы остаются у того, кто собирал, и в образ не попадают. Внешнего сборщика ошибок, которому их можно было бы отдать, у установки в вузе нет; ошибки в консоли и на странице ошибки читаются по сообщению, а воспроизводятся на `vite` с исходниками. Иконки lucide собираются в один чанк `icons` (Rolldown `codeSplitting.groups`): 16 КБ gzip грузятся с первой страницей, зато JS-файлов 195 → 163, у главной 54 → 41, у страницы шага 90 → 63. Страница 404 загружается по требованию, иллюстрации ушли из начальной загрузки (JS первой страницы: 206 → 192 КБ gzip). Маршруты проекта сами запрашивают шаблон, проект, список шагов и шаг (модуль `incubator/prefetch` подгружается вместе с маршрутом, чтобы не утяжелять входной бандл); шаг, полученный маршрутом не раньше 5 с назад, открывается сразу, а значения, оставленные в кэше редактором прошлого визита, помечены как устаревшие и запрашиваются заново.
**Альтернативы.** Hidden source maps в образе (их всё равно отдаёт nginx); группа «вся дизайн-система» одним чанком — начальная загрузка выросла до 290 КБ gzip, отклонено; `entriesAware` для иконок — нечитаемые имена файлов и почти тот же выигрыш.

## D-074. «Скрывать чувствительные данные»: какие поля, от кого и где
**Контекст.** Флаг проекта `hide_sensitive` хранился, но ничего не скрывал (аудит, С-1), а интерфейс обещал «юнит-экономика и технология не видны никому вне команды».
**Решение.** Чувствительные поля помечены в шаблоне (`sensitive: true`, отдаются в `TemplateField.sensitive`): весь шаг «Юнит-экономика» (`unit`, `price`, `variable_cost`, `cac`, `purchases`, `assumptions`) и в шаге «Решение» — «Новизна» (`novelty`: технология, подход) и «Нечестное преимущество» (`unfair_advantage`: экспертиза, данные, доступ к рынку). Колонка таблицы чувствительной быть не может. «Своими» считаются команда (владелец и участники) и научный руководитель проекта: руководитель одобряет шаги, и скрыть от него юнит-экономику значило бы одобрять вслепую. Остальным — руководству вуза, innovation manager и администратору вне команды — при включённом флаге не отдаются: значения этих полей (`Step.withheld` называет скрытые поля; минимум для завершения считается по всем ответам и называет поля, но не их содержимое), их история (`ListRevisions` с `hidden_fields`), AI-проверка шага с такими полями (её советы пересказывают ответы), диалоги с ментором — все, а не только по этим шагам (`MentorConversation.withheld`): вопросы команды и ответы модели могут цитировать любые данные проекта, а вырезать их из свободного текста надёжно нельзя; материалы, при сборке которых в данных были чувствительные ответы (`project_materials.sensitive`, миграция 00012; материалы, собранные до неё, считаются чувствительными): их нет в списке, скачивание — 404. Сами материалы для команды собираются из всех данных — это её документы. Витрина не берёт эти поля никогда, независимо от флага: предзаполнение из инкубатора вырезает их до сборки, остальное команда пишет сама. Лента активности и комментарии не меняются: в ленте только названия полей, комментарии — слова людей, которые знают, кто их читает.
**Вне решения: AI-оценка.** Отчёт оценки читают руководитель и innovation manager, и по рубрике вуза (D-041) юнит-экономика — часть критерия «бизнес-модель»: оценка без неё занижала бы балл, а текст модели (обоснования, red flags) отфильтровать надёжно нельзя. Поэтому оценка видит все данные, а интерфейс прямо говорит, что флаг на неё не влияет; вариант для вузов, которым это важно, — B-032.
**Последствия.** Скрытие — на сервере, по роли в проекте (`project.Access.SeesSensitive`); интерфейс только объясняет, что скрыто. Включение флага не отзывает то, что уже успели скачать или прочитать до него.

## D-075. Повторная модерация публичной страницы и снятие модератором
**Контекст.** По D-043 правки одобренной публичной страницы публиковались сразу; одобрение было разовым (С-8): безобидную страницу можно было одобрить и заменить спамом, модератор в составе команды одобрял свою страницу, снятие модератором не закреплялось.
**Решение (меняет D-043).** Изменение того, что публичная страница показывает (адрес, название, слоган, разделы, видео, теги, «что нужно», обложка — загрузка и удаление), возвращает одобренную страницу на модерацию (`in_review`); до одобрения она видна только внутри вуза, уходит с национальной витрины, из sitemap и каталога. Выбран этот вариант, а не «показывать последнюю одобренную версию»: он не требует хранить вторую копию страницы и учить ей каталог, поиск, SEO, OG-картинки и национальную витрину; цена — проект на время проверки пропадает с публичной витрины (B-033, если это станет проблемой). Настройки, которые ничего не меняют в показе (`show_score`, `contact_enabled`), и состав команды (он берётся из проекта) повторной проверки не требуют. Одобрение называет версию, которую модератор видел (`If-Match: "<version>"`, без него 428, устаревшая — 412) и публикует ровно её; модератор из команды или руководитель проекта свою страницу не одобряет (`showcase.own_page`); отклонение версию проверяет, если она передана. Снятие с витрины модератором вне команды (`unpublish`) ставит страницу на удержание (`held`): публикация командой — любая, и «для вуза» тоже — отправляет её на проверку и не делает видимой, пока модератор не одобрит; снятие самой командой удержание не снимает. Ответы на загрузку и удаление обложки, публикацию, снятие и решение модератора отдают `ETag`.
**Последствия.** Поток «опечатка → повторная проверка» увеличит очередь модерации; это осознанная плата за то, что публично видно только проверенное. Модератор видит в очереди версию страницы и её статус удержания.

## D-076. Порядок блокировок проекта и его частей
**Контекст.** Одновременное завершение двух шагов теряло одно увеличение `completed_steps` (Н-19), а лимит команды проверялся без блокировки (Н-13). Первая попытка заблокировать строку проекта `FOR UPDATE` приводила к взаимоблокировкам: вставка шага, участника или страницы витрины берёт на проект `KEY SHARE` по внешнему ключу.
**Решение.** Кто меняет проект вместе с его частями — прогресс шагов, состав команды, страницу витрины, — сначала берёт строку проекта `SELECT … FOR NO KEY UPDATE` (`project.Service.Lock`), затем свои строки. Этот режим не конфликтует с `KEY SHARE`, но конфликтует сам с собой: такие записи выполняются по очереди, и каждая следующая видит то, что зафиксировала предыдущая (READ COMMITTED берёт новый снимок на каждый запрос). Счётчик прогресса пересчитывается после блокировки; команда считается под ней.
**Последствия.** Записи одного проекта сериализуются — для учебной командной работы это незаметно. Новый код, меняющий проект и его части, берёт блокировку проекта первой.

## D-077. Размер команды и передача проекта модератором
**Решение.** В команде до 12 человек (владелец и участники); научные руководители в это число не входят, их до 3 (`project.supervisors_full`). Лимит проверяется под блокировкой проекта. Передать владение может владелец, а если он ушёл из вуза или заблокирован (членство не активно) — innovation manager или администратор вуза (`project.owner_active`, пока владелец активен); прежний владелец становится участником, передача пишется в аудит с отметкой модератора. Участники и комментарии архивного проекта не меняются.
**Последствия.** Добавление участника по-прежнему без его согласия: приглашения с подтверждением и связь с доской «Ищу в команду» — B-031.

## D-078. Изображения: лимиты до декодирования и очередь декодирования
**Контекст.** Изображение до 40 Мп декодировалось целиком, обложка ещё и копировалась: PNG около 100 КБ занимал сотни мегабайт, параллельные загрузки роняли API (С-12).
**Решение.** Размер читается из заголовка до декодирования: не больше 16 Мп и 8192 px по стороне (12-мегапиксельное фото телефона проходит; аватар — 512 px, обложка — 1600×900). Одновременно декодируются не больше двух изображений на процесс API (ожидание обрывается вместе с запросом), то есть в худшем случае около 256 МБ (16-битный PNG). Обложка масштабируется прямо из декодированного изображения: центральный прямоугольник при повороте по EXIF остаётся центральным, поэтому кадр вычисляется по исходнику, а поворачивается только маленький результат — второй полноразмерной копии нет. Аватары и обложки одного участника вместе — не больше 10 подряд и 30 в час (`rate_limited`).

## D-079. Языковые версии публичных страниц
**Контекст.** Страницы, которые рисует сервер (D-045, D-050), отдавали заголовок и описание на языке вуза, первый экран — на языке посетителя, и у поисковика была одна казахская версия (Н-35); национальная витрина имела canonical на домене каждого вуза.
**Решение.** Язык страницы выбирается одинаково на сервере и в клиенте: `?lang=` в адресе, затем cookie `qadam_locale` (выбор пользователя), затем `Accept-Language`, затем казахский; ссылка с `?lang=` сохраняет выбор, как переключатель языка (`public/theme-init.js`, `detectLocale`). На этом языке вся страница: `<html lang>`, заголовок, описание, JSON-LD, первый экран. Каждая страница перечисляет версии `hreflang` (`kk`, `ru`, `en` с `?lang=` и `x-default` — адрес без него, язык которого следует за посетителем); canonical — адрес этой версии. Национальная витрина одна для всех вузов: её canonical и версии — на сайте платформы (`PUBLIC_URL`), и в sitemap она есть только у него.
**Последствия.** Поисковик индексирует три языковые версии; `Vary: Accept-Language, Cookie` у страниц сохраняется.

## D-080. Питч-дек — 12 слайдов в классическом порядке
**Решение.** По ТЗ в питч-деке 10–12 слайдов: схема ответа модели требует от 10 до 12, промпт `materials@2` просит ровно 12 в классическом порядке, а слайд, для которого в проекте нет данных, — один пункт «что команде ещё добавить» вместо догадок. Mock собирает все 12 так же. Это заменяет прежнее «пустые слайды выпадают» (D-039).
